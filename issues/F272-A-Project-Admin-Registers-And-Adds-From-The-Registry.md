# F272 — A Project Admin Registers And Adds From The Registry

**Status:** Implementing.
**Size:** M - about a day adapting the existing bring, signed access edits and sync retries to registry people and project-scoped actions.

**What must be true.** A project admin whom `hosts/<host>/access.yml` admits sees "admitted on host X" and *Register the project*, which brings the project to the host in one click (today's bring without pasted values or key paths). *Add a developer* is a pick from the registry's persons; it commits the access file signed by the project admin, brings it to the host and asks for the sync ([F252](README.md#f252), [F253](README.md#f253)). *Remove from the project* is chosen from the project's person list. *Lock in this project* marks the person `locked` in the access file, signed, brought to the host and synced: their access to this project's repositories and rooms goes, their account and other projects stay; *Let back in* undoes it. A person whose key changed without the predecessor's signature cannot be picked, unless an admin replaced their lost or stolen key in the access file ([F280](README.md#f280)). A project admin who may not do something sees who may, with their email where their card names one.

## Why

One-click joining from signed state, the flow's steps 4, 5 and 7.

## Acceptance

- An admitted project admin sees the named host and registers the selected verified project with one click. No pasted public values, key paths or secret fields intervene. Missing admission, a mismatched access address, an unverified project or unavailable signing agent prevents publication and upload with a reason.
- Register succeeds only after the host confirms the intended project and revision. Repeated clicks while busy do not register twice. Failed delivery remains retryable without repeating a published access change.
- Add chooses a Core-eligible registry person and signs and publishes their login, role and fingerprint before uploading and syncing the exact access revision. Refused cards and unapproved key changes produce no mutation. An authorized lost-key replacement is accepted only for the access scope Core confirms.
- Remove, lock and let back in change only the selected project's access. A host stand-in with two projects observes the locked person's repositories and rooms removed only from that project, while the account and other membership remain. Unlock restores only the retained membership. No success is inferred from process exit alone.
- Unfiled receipts resolve by request ID before any obsolete selection is discarded. A filed receipt is superseded, with Discard, only by a typed verdict: Core refuses that exact request and revision, Core proves the verified access revision excludes it, or the server was given back. Every other refusal or error keeps the receipt filed or delivered with Retry; a delivered receipt is never superseded, and confirmed registrations stay. Developers are directed to the project admins Core names; project admins missing host admission are directed to host admins.
- Publication failure causes no host change; upload failure causes no sync; a wrong project or access revision cannot confirm success. Restart and retry finish the pending delivery without another commit. The targeted VM check later verifies the actual Machines registration and project sync effects.

## To be checked

- Nothing below was run live: every Core and host command was read from Core's `doc/commands.md` and `doc/hosts.md` on its `main` and from porelo-host's `main` (`roles/porelo/files/porelo-host-person`, its sudoers file, `roles/forge/files/porelo-host-project`, `roles/forge/tasks/own.yml`, `doc/local-forge.md`), and is proven only against test stand-ins.
- The host has no own-account registration a project admin can run without a hand step. Registration on the host is root's `porelo-host-project add <project> <admin> --signed-by <key>` (no sudoers rule for a person), and the forge's organization, teams and room come from the own-account bring (`porelo.host.bring`), which needs a machine file and a stop that fills the vault, and answers Ansible steps rather than the project and access commits. Until porelo-host offers one, *Register the project* ends at the host's `sync`, which refuses in its own words ("project <p> is not registered on this host", or "run bring first") until both were done by hand.
- The host's `sync` answers whom it `added`, `dropped` and `refused`, not each person's state: Add confirms a person only when this sync added them, so a sync whose answer was lost and that runs again (`unchanged`) cannot confirm the person, and Lock and Let back in cannot be confirmed at all. A read of the project's applied membership on the host is needed from porelo-host.
- Which head `project verify` takes from a bundle is not written down; the bundles carry exactly the change's commit as both `HEAD` and `main`, as the bring's do.
- What `project access init` calls an empty repository: the change needs the access repository's head commit as its base, so an access repository with no commit at all is refused with words.
- Whether `project access add --host --card --role admin` takes an admin already in the access file (Register on a further host, or again).
- Core serves no project-scoped picker verdict and no lost-key-replacement verdict: the picker offers the registry's trusted cards, and Core refuses a card it does not take when the person is filed.
- Core's `project verify` names the signer of the project tip only, not of the access commit. A filed commit is taken as the change's own only when git verifies its SSH signature against the actor's key alone (an allowed-signers file of that one key, `gpg.ssh.revocationFile` the person's `revoked.krl` when there is one); an `access_signer` in Core's answer would let Core decide that too.
- The access repository is read from `project.yml` at the commit Core's follow holds in force, never at the project copy's unverified head; a project file that moved its access repository after that commit is refused until Core's follow takes it.
- The targeted VM check of Register and Add against Core's and porelo-host's packages.

## Implementation boundary

- `ProjectAccessCore` supplies the verified followed project YAML, project/access revisions, actor login/fingerprint, pinned admission fingerprint, active signer keys, signing availability, scoped eligible fingerprints and authorized lost-key replacements. The accepted registry must independently name the same host, project admin and access repository.
- A `ProjectAccessChange` carries a durable request ID, host and immutable host card, project, access repository, project/base-access revisions, actor login/fingerprint, action, and optional person login/role/fingerprint/locked state. Core signs once per ID, resolves already-filed IDs without requiring current signing authority, and rejects stale bases; publication retries that exact revision. Core separately authorizes publication and delivery of that exact filed request using its signing-time authority, so a self-removal can finish delivery without retaining authority to sign further changes. Revoked identities and removed host admission still refuse delivery. A read-only exact-publication check reconciles a lost push receipt before requiring authority to publish again.
- `ProjectAccessTransport` connects through the accepted card and agent, confirms private project/access bundle intake, and returns observed host, project, project revision, access revision and project-only membership states. No command or additional socket format is assumed.
- A change whose server was given back before Core's change was recorded is forgotten when the server is marked given back, in whatever state it reached (unfiled, filed, delivered or superseded, and also mid-run); Retry ends cleanly, and a registration that ended so says nothing was registered instead of saying "The server was given back".
- `ProjectAccess.rememberMachine` is an injected idempotent local recording operation (the application's `Machines.add`), shared by registration and direct delivery retry. `Settings.projectRegistrations` stores the confirmed registration independently of `projectAccess`; both use the checked explicit lifecycle shape. Legacy boolean receipts migrate on read, retaining their request ID and exact revision. Superseded-receipt cleanup never changes the separate confirmed record.
- The stand-in measures project repository and room removal while retaining the account and other project membership. Preservation of unrelated access settings belongs to Core and remains to be verified with its actual adapter; a fixture that never edits those settings cannot measure it. Served Core fields, actual HostRun delivery and the targeted VM effects still need confirmation before live use.

## Deferred

- Remove, Lock, Let back in and accepting a new key are listed unavailable in the app ("not connected to Core and the host yet") and Core is never asked for them, since the host's answer cannot confirm them (see *To be checked*).
- Core's filing commits and pushes in one step, so publication only confirms that the access repository holds the exact filed commit; a filed id is looked up by Core's `Porelo-Change-Id` trailer in the access repository's history, there being no read-only Core verb for it. A commit is taken only when it is the one commit carrying the id, once, made on the change's base alone, signed by the actor's key, verified by Core from the access commit in force here, and shows the person with the role and key the change names; any other is refused, never delivered.
- Automatic central-forge collaborator grants and revocations; central-forge access remains a prerequisite.
- New list and item pages; the shared project commands and minimal dialog wiring are available for page integration.
- A filed registration is still held to the project state it names before Core is asked, so a registration Core refused after a project commit is retried rather than superseded.
- The Core adapter's filing maps only its conflict to a typed answer; another filing failure leaves an unfiled receipt that files again with the same request ID.
